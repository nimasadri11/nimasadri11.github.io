The Software That Will Never Need Another Update

grep, SQLite, curl, TeX — and what they teach us about building things that last

grep was written in 1973. awk in 1977. TeX was declared finished by Donald Knuth in 1990. SQLite hasn't broken backwards compatibility in over twenty years. curl has been shipping since 1998 without a single breaking change to its API.

These programs are done.

Not dead. Not abandoned. Not “legacy.” Done — the way a hammer is done. They solved their problems. They carry the load. They've been carrying it for decades. And they'll keep carrying it long after we're all migrating to whatever framework ships next Tuesday.

The Gallery of Done Software

TeX. Knuth started writing it in 1977 and declared the design frozen in 1990. Its version number converges toward pi — currently 3.14159265. When Knuth dies, the version freezes at exactly pi, and any remaining bugs become permanent features by definition. The man wrote a typesetting system so correct that his final act of confidence was making all future errors definitional. TeX has been essentially unchanged for over 35 years. Every academic paper you've ever read was probably typeset with it.

SQLite. It runs on every phone on earth. Every Mac. Every Windows PC. Every web browser. Every copy of Skype, iTunes, and Dropbox. It's probably the most deployed piece of software in human history, and it's essentially maintained by one person. SQLite has over 90 million lines of test code — roughly 590 times more test code than source code. Not because they're paranoid. Because when you ship inside every device on the planet, you don't get to push a hotfix. The result: over two decades without a breaking API change. The SQLite developers have pledged to support it through the year 2050. Their stated goal: “make the content you store in SQLite today as easily accessible to your grandchildren as it is to you.”

curl. Daniel Stenberg has been maintaining it since 1998. It runs on everything from Teslas to Nintendo Switches to Mars rovers. It has never broken backwards compatibility. Scripts written against curl in 2003 still work today, unmodified. Stenberg treats backwards compatibility as a promise, not a constraint. He treats his API the way a stonemason treats a cathedral wall — you build it once and you build it right.

The Unix tools. sort. grep. sed. awk. cat. wc. Written in the 1970s, still doing exactly what they did then. Their interfaces are ugly by modern standards — cryptic single-letter flags, no color output, man pages that read like assembly documentation. But they work. They compose. And a shell script that pipes grep into awk into sort runs the same today as it did when Jimmy Carter was president.

These aren't relics. They're the greatest hits of our industry. Each one represents the rarest thing in software engineering: a program that solved its problem so completely that it never needed to be solved again.

We should be building more things like this. Instead, we're building the opposite.

The Horror

I mass-merged fifteen Dependabot PRs this morning. Didn't read a single changelog. Three of them were for transitive dependencies four levels deep — packages I've never heard of. npm audit was yelling about six “critical vulnerabilities,” all in dev dependencies that never touch production. You do the same thing. Everyone does.

A fresh create-react-app pulls in nearly 1,500 packages. To render a div. The lockfile alone is 40,000 lines and you couldn't name what half those packages do.

Last week a colleague's app broke in production because a package they used depended on a package that depended on a package that shipped a “minor” version bump that wasn't minor. Nobody did anything wrong. The dependency graph itself is the problem.

In 2016, a developer unpublished an 11-line npm package called left-pad — a function that pads a string with spaces. It broke React. It broke Babel. It broke thousands of projects across the internet. Eleven lines of code that half the JavaScript ecosystem depended on, written by a stranger, controlled by no one. We didn't learn anything from it. Six years later, a maintainer of colors.js and faker.js — packages downloaded tens of millions of times per week — deliberately sabotaged his own code to protest not being paid. He pushed an infinite loop to npm and broke CI pipelines across Fortune 500 companies. The whole edifice shook because one tired person decided to stop holding it up for free.

This is the foundation we're building on.

You spend somewhere between 5 and 10 hours a week on maintenance that has nothing to do with your actual product. Updating deps. Fixing CI. Chasing deprecation warnings. Migrating to a new major version of a framework that renamed half its methods and changed the config format for the third time. This isn't engineering. It's a tax. And it compounds every week. And now AI agents are writing code that pulls in even more dependencies — because they don't feel the pain of maintaining them.

We've built our software on foundations we can't inspect, maintained by strangers we've never met, funded by no one.

There was a thread on Hacker News recently where a 60-year-old developer said the reason he quit was “the never-ending rat race of keeping up with the latest bizarre web stacks.” Over a thousand people upvoted it. Nobody disagreed.

And we call this progress.

What “Done” Actually Means

The programs in the Gallery didn't end up this way by accident. There's a pattern.

Solve one problem. grep finds patterns in text. It doesn't also format text, compile text, or serve text over HTTP. If you solve one well-defined problem, and the problem doesn't change, your software doesn't need to either.

Depend on nothing. SQLite has zero external dependencies. curl can be built with or without optional libraries. TeX ships as a single program. Every dependency is a bet that someone else will maintain their code forever. That's a bad bet.

Get the interface right, then freeze it. curl has added flags over 28 years but has never removed or changed one. grep's interface hasn't changed in 50 years. The interface is the contract. Once people depend on it, changing it costs more than any new feature could justify. This matters even more now that agents write code — they can use curl reliably because the interface is stable. A library that ships breaking changes every six months is a library agents will get wrong.

Test like you won't get another chance. SQLite doesn't have 90 million lines of test code because they're obsessive. They have them because they ship into environments where “just push a patch” isn't an option. If you want software that doesn't need updates, you catch the bugs before you ship — because you're not shipping again.

Choose boring technology. Every program in the Gallery is written in C. Not because C is the best language. Because C will be here in 50 years. If you build your software on this year's hot framework, you'll be rewriting it when the ecosystem moves on. Done software is written in languages that will outlive their authors.

The Paradox

Here's what nobody talks about.

The best software disappears. You don't think about grep. You don't think about SQLite. You don't think about the JPEG decoder or gzip or the DNS resolver running on your machine right now. They're just there. Working. Silently. While you're over here fighting with your node_modules folder and mass-merging Dependabot PRs and reading migration guides for React 47.

The software that demands your constant attention is the software that isn't done yet. And most modern software will never be done — not because the problems are harder, but because it was never designed to be finished. It was designed to be iterated on. To “evolve.” To grow.

But growth isn't always progress. Nobody promotes the engineer who writes a tool that works for twenty years without changes. There's no conference talk in “I built a thing and then I stopped.” The industry has convinced itself that shipping is the only virtue, that velocity is the only metric, that if you're not iterating you're dead.

Meanwhile, grep just sits there. Working. For half a century.

Sometimes a program is finished the same way a proof is finished. There's nothing to add and nothing to take away.

The Challenge

Can you build something this year that will work, unchanged, in 2036?

Not an app with a database and a frontend and 47 API integrations. Something small. Something focused. A CLI tool. A file format parser. A compression utility. A text processor. Something with zero dependencies, a stable interface, and a test suite that would make the SQLite team nod.

Write it in a language that will outlive you. Give it an interface you'd be comfortable freezing forever. Test it until you trust it more than you trust yourself.

Then stop. Put it on a shelf. Come back in ten years. If it still works — no updates, no migrations, no breaking changes, no Dependabot PRs — you've done something that almost nobody in this industry does anymore.

You've built something that's done.
